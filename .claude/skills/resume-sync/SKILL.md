# resume-sync

입력: `$ARGUMENTS`

첫 단어는 프로젝트 이름이고, 나머지는 중점 지시다. 나머지가 특정 영역·작업을 가리키지 않는 일반 요청(`새로 추가해줘`, `최신 내용으로 업데이트해줘` 등)이면 중점 지시 없음으로 본다. 중점 지시는 없을 수 있고, 없으면 되묻지 않는다. 입력이 비어 있으면 프로젝트 이름부터 묻는다.

이력서에는 프로젝트의 **구조·아키텍처 결정**만 남긴다. 커밋·PR·버그 단위 내용은 근거로만 쓰고 옮겨 적지 않는다.

## 1. 레포 찾기

- `~/Documents/GitHub/wr/` 의 폴더 이름과 맞춘다. `-`/`_` 와 대소문자는 무시한다 (`foo-bar` → `foo_bar`). 맞는 폴더가 없거나 여럿이면 후보를 보여 주고 고르게 한다. 이후 단계에서 프로젝트 이름은 실제 폴더 이름을 쓴다.
- `wr/` 자체가 없으면(맥 등) 경로를 묻고, 이 스킬에 그 경로를 추가하자고 제안한다.

## 2. 최신화

`git -C <repo> fetch --all` 만 한다. fetch 는 working tree 를 바꾸지 않으므로 "wr 은 읽기만" 규칙과 맞는다. 건너뛰지 않는다. pull · checkout · 파일 수정은 하지 않는다. fetch 가 실패하면 알리고 로컬 기준으로 갈지 묻는다.

실제 레포 이름과 기본 브랜치는 `cd <repo> && gh repo view --json nameWithOwner,defaultBranchRef` 로 한 번에 얻는다. `gh` 에는 `git -C` 같은 옵션이 없어서, 레포 밖에서 돌리면 이력서 레포의 값이 나온다. 이후 `gh` 명령에는 모두 `-R <nameWithOwner>` 를 붙인다. 기본 브랜치를 git 에서 읽지 않는 건 클론에 `origin/HEAD` 가 없을 수 있어서다.

fetch 는 로컬 파일을 갱신하지 않는다. 로컬 브랜치가 기본 브랜치와 다르거나 뒤처져 있으면(`git rev-list --left-right --count HEAD...origin/<기본 브랜치>`), 4단계의 구조 근거는 origin 기준으로 본다. 파일은 `git show origin/<기본 브랜치>:<경로>`, 폴더 구조는 `git ls-tree -r --name-only origin/<기본 브랜치>` 로 읽는다.

## 3. 범위 정하기

`docs/resume-sync.md` 에서 폴더 이름으로 이 프로젝트 행을 찾는다. 이 파일은 비공개 레포 이름이 들어가서 gitignore 된 기기별 기록이다. 파일이 없으면 행 없음으로 본다. 아래 표는 위에서부터 처음 맞는 상황을 따른다.

| 상황              | 볼 범위                                                                                                                                                                                                                        |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 중점 지시 있음    | 기준 시각을 무시하고 그 영역의 전체 이력                                                                                                                                                                                       |
| 행 있음 (재실행)  | 기준 시각 이후(커밋은 `--since=<기준 시각>`, PR 은 `--search "updated:>=<기준 시각의 날짜>"`). 결과는 기존 activity 에 대한 추가 / 수정 / 삭제 제안이 된다. 메모 칸에 레포 밖 근거나 진행 중 항목이 있으면 그 상태도 다시 본다 |
| 행 없음 (첫 실행) | 레포에서 내 첫 커밋부터. 따로 묻지 않고, 1차 질문에서 범위를 알린다                                                                                                                                                            |

## 4. 근거 모으기

- **구조 (주 근거)**: README, CLAUDE.md, DESIGN.md, `docs/`, 결정 기록·ADR, `package.json` · workspace 구성, 최상위 폴더 구조를 본다.
- **내 커밋**: `--author=eeennsu` 로 거른다. 내 작성자 주소는 여럿이지만 모두 이름이나 주소에 `eeennsu` 가 들어 있다. 주소를 이 파일에 적지 않는 건 이 레포가 공개라서다.
  - 예: `git log --all --no-merges --author=eeennsu`
  - 내 첫 커밋: 같은 명령에 `--reverse --format=%cI` 를 붙이고 `| head -1`
  - 영역별 비중: `git shortlog -sne --all --no-merges -- <dir>`
- **내 PR**: 원격 URL 은 레포 이전 전 주소일 수 있다. 이 경우 `--author` 필터가 에러 없이 빈 결과를 낸다. 그래서 2단계에서 얻은 실제 이름으로 `gh pr list -R <nameWithOwner> --author eeennsu --state all --limit 200` 을 돌린다.
- **레포 밖 근거**: 중점 지시가 가리키는 작업이나 후보의 상태(앱 채택 여부 등)가 다른 레포나 머지 안 된 브랜치에 있을 수 있다. 그 레포 이름은 이 레포의 CLAUDE.md 나 결정 기록에서 찾는다. `gh` 로 읽기만 하고, 그 사실을 사용자에게 알린다. PR 없는 브랜치는 `gh api repos/<owner>/<repo>/branches/<브랜치>` 로 있는지 본다.

## 5. 후보 만들기

후보 하나는 **최종 구조·아키텍처 결정 하나**다. 무엇을 어떤 구조로 만들었고 왜 그렇게 했는지를 담는다.

다음은 후보가 아니고, 후보를 뒷받침하는 근거로만 쓴다.

- 버그 수정, 컴포넌트 하나의 수정, 스타일 규칙, 수치 하나
- 나중에 뒤집힌 중간 결정

각 후보에는 다음을 붙인다.

- 한 줄 요약
- 근거 파일
- 내 기여: `주도` 또는 `참여`. `참여`는 그 영역에서 내 커밋이 절반 미만인 경우다. 내 커밋이 거의 없으면 후보에서 뺀다.
- 상태: 사실대로 짧게 쓴다 (`머지됨`, `진행 중`, `결정만 머지됨` 등). 질문과 보고에만 쓰고 yaml 에는 옮기지 않는다(7단계).

중점 지시와 맞는 후보를 맨 위에 두고 깊게 정리한다. 나머지 후보는 한 줄씩만 덧붙인다. 중점 지시가 없으면 내 커밋이 많이 들어간 후보부터 깊게 정리한다. 기존 activity 와 주제가 겹치는 후보는 겹친다고 표시한다. 후보는 몇 개를 보여 줘도 된다. 다만 activity 하나의 subject 는 기존 것을 포함해 최대 4개다.

## 6. 묻기

질문은 번호를 붙인 텍스트로 보내고 답을 기다린다. 사용자가 답하기 전에는 YAML 을 쓰지 않는다.

**1차: 범위 알리기 + 후보 고르기**

- 맨 위에 본 범위를 알린다(첫 커밋부터 / 기준 시각 이후 / 중점 영역 전체).
- 번호로 고르게 하고, 고른 후보마다 `중점` / `가볍게` 를 같이 받는다. 사용자가 비중을 말하지 않으면 모두 `중점`으로 본다. `참여` 후보는 "참여로 적을지, 뺄지"를 같이 묻는다.
- 재실행이면 추가 / 수정 / 삭제 제안을 고르게 한다.
- 고른 것을 더하면 subject 가 4개를 넘으면, 어떤 후보끼리 합칠지 묶는 안을 하나 추천하고, 그 안으로 갈지 새 activity 로 나눌지 묻는다. `가볍게` 후보부터 합친다.
- 바뀐 게 없으면 "변경 없음"이라고 알리고 여기서 끝낸다.

**2차: 한 메시지에 묶어서 묻기**

1. **배치**: 기존 `(주)원더라운드` activity 중 어디에 넣을지, 아니면 새 activity 를 만들지. 새 activity 면 아래 초안을 제시한다.
   - `id`: `wonder-<주제>-<시작연도>`
   - `title`, `shortTitle`
   - `startDate`: 레포에서 내 첫 커밋 날짜, `'YYYY.MM.DD'` 형식
   - 진행 중이면 `endDate` 를 두지 않는다
2. **빈 곳**: 근거 문서에 없는 것 중 두 가지만 묻는다. 모르면 비워 두고, 지어내지 않는다.
   - 배경: 누가 무엇을 요청해서 시작했는지, 어떤 문제를 풀려고 했는지
   - 성과 수치: 전 / 후를 비교할 수 있는 숫자(작업 기간, 비율 등). activity 전체의 결과인지 특정 후보의 결과인지도 같이 받는다
3. **`skill.yaml`**: 이번 근거에서 쓴 기술 중 `src/subjects/*/skill.yaml` 에 없는 것을 후보로 보여 준다. 넣는다면 어느 category 에 넣을지도 같이 제시한다.
4. **velog 매핑**: 새 activity 일 때만 다룬다. 매핑은 `techTags` 와 태그가 하나라도 맞는 velog 글을 전부 그 activity 카드에 붙인다. 후보 태그(`src/shared/utils/utilMapTagToSkill.ts` 의 `TAG_TO_SKILL` 값)마다 `src/data/velog-posts.json` 에서 걸리는 글 수와 제목 2~3개를 보여 준다. 이 activity 주제를 다룬 글이 걸리지 않으면(0건이거나, 다른 activity 에 붙는 글만 걸리면) "매핑하지 않음"을 추천한다. 매핑이 없으면 카드의 관련 글이 비어 있을 뿐이다.

## 7. 쓰기

| 파일                                   | 할 일                                                                                                                                                                                                                                                                                                                               |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `src/subjects/ko/experience.yaml`      | `(주)원더라운드` 의 activities 에 넣는다. 위치는 `startDate` 내림차순                                                                                                                                                                                                                                                               |
| `src/subjects/en/experience.yaml`      | ko 가 기준이다. 같은 위치에 번역해 넣는다. 대상 activity 가 en 에 없으면 그 activity 전체를 번역해 추가한다                                                                                                                                                                                                                         |
| `src/data/activity-velog-mapping.yaml` | 2차에서 매핑이 승인됐을 때만, 맨 앞(헤더 주석 다음)에 `- activityId: <id>` 와 승인된 `techTags` 를 추가한다                                                                                                                                                                                                                         |
| `src/subjects/{ko,en}/skill.yaml`      | 승인된 항목을 승인된 category 끝에 넣는다                                                                                                                                                                                                                                                                                           |
| `docs/resume-sync.md`                  | 이 프로젝트 행을 추가하거나 갱신한다. 파일이 없으면 `\| 프로젝트 \| 기준 시각 \| activity id \| 메모 \|` 표로 새로 만든다. 기준 시각은 fetch 뒤 `git -C <repo> log -1 --all --format=%cI` 값. activity 가 여럿이면 쉼표로 적는다. 메모 칸에는 레포 밖 근거(기준 시각이 그쪽 변경은 잡지 못한다)와 진행 중 항목의 실제 상태를 적는다 |

activity 형식:

- 고른 후보 하나가 subject 하나가 된다. subject 는 activity 전체 기준으로 **2~4개**다.
- subject 마다 details 는 **1~3줄**이고, 한 줄은 1~2문장이다. 기존 subject 는 이번에 고칠 때만 이 형식에 맞추고, 건드리지 않는 항목은 그대로 둔다.
- `가볍게` 후보는 details 1~2줄의 짧은 subject 로 쓰거나, subject 를 따로 두지 않고 다른 subject 의 한 구절로 넣는다.
- `problem` / `solution` 쌍은 근거 문서나 2차 답(배경)에 문제 상황이 있을 때만 쓴다. 2차에서 받은 배경과 전 / 후 수치는 activity 전체의 것이면 첫 subject 의 `problem` / `solution` 에, 특정 후보의 결과면 그 subject 에 넣는다. 사용자가 범위를 말하지 않았으면 activity 전체의 것으로 본다. 수치에는 사용자가 말한 원인만 붙인다.
- 문체는 기존 항목을 따른다: 명사형 종결(`~구축`, `~설계`).
- 한 줄은 세 가지를 섞어 쓴다. `problem` 줄은 상황만 써도 된다.
  - 뼈대: 무엇을 왜 그렇게 했는지 쓴 문장
  - 전문 용어: 설계 개념은 업계 용어 그대로 쓴다(디자인 토큰, 단일 원천, 빌드 파이프라인, 관심사 분리, 권한 가드, 버전 고정, 점진적 마이그레이션). 일상어로 바꾸지 않는다
  - 기술 이름: 그 일을 맡은 패키지(라이브러리·프레임워크·도구)와 플랫폼 표준 기능의 이름 1~3개를 백틱으로 붙인다(`Tamagui`, `Style Dictionary`, `ESLint`, `react-native-web`, `WebView`, Claude Code `hook`)
- 바꿔 쓰는 것은 패키지·플랫폼 안의 함수·옵션·설정 키 이름(`createTamagui`, `import.meta.glob`, `PreToolUse`, `includeFontPadding`)뿐이다. 그 이름이 하는 일을 가리키는 전문 용어로 바꾼다.

  | 식별자 나열                                                                           | 너무 쉬운 말                                                        | 이렇게 쓴다                                                                                                                                             |
  | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | `DTCG` 토큰 JSON → `Style Dictionary` 빌드로 `Tamagui` 테마 · CSS 변수 · TS 상수 출력 | 색 · 글자 값을 한 곳에서 관리하고 앱과 웹이 자동 변환해 쓰도록 구성 | 디자인 토큰을 단일 원천으로 두고, `Style Dictionary` 빌드 파이프라인이 앱(`Tamagui` 테마)과 웹(CSS 변수) 출력으로 각각 변환하도록 구성                  |
  | `PreToolUse` hook 이 `CLAUDE.local.md` 역할을 읽어 `gh pr merge` · `git push` 차단    | 명령을 실행하기 직전에 작업자를 확인해 위험한 명령을 막도록 구성    | Claude Code `hook`으로 명령 실행 전에 작업자 역할을 검사하는 권한 가드를 두어, 비개발자 세션의 `main` 직접 반영 · PR 병합 · 배포 실행을 차단하도록 구성 |

- 이 레포는 공개이고 wr 레포는 비공개다. 그래서 커밋되는 모든 것(yaml 의 문구, activity `id`, `skill.yaml` 항목, velog 매핑)에 사내 제품명·레포명·사내 패키지명·내부 URL·사람 실명을 쓰지 않는다. 제품은 "자사 앱", 사내 패키지는 "앱용 컴포넌트 패키지"처럼 일반명으로 바꾼다. 공개 라이브러리 이름은 그대로 쓴다.
- 진행 중인 작업도 완성된 구조로 쓴다. yaml 에는 "진행 중"·"도입 예정" 같은 상태 표현을 넣지 않는다. 실제 상태는 9단계 보고와 `docs/resume-sync.md` 메모 칸에 적는다.

## 8. 검증

1. **id 검사**: 쓰기 전과 쓴 후에 `bun scripts/verify-experience-ids.ts` 를 돌린다. ko 와 en 의 activity id 가 같은 순서로 있어야 통과한다.
   - 쓰기 전부터 실패하면 en 이 ko 를 못 따라간 것이다. 사용자에게 알리고, en 을 ko 에 맞출지 묻는다.
   - 쓴 후에는 통과해야 한다.
2. **서식**: `bunx prettier --write <고친 yaml 파일들>` 를 돌린다. 커밋할 때 lint-staged 가 하는 일과 같고, YAML 문법 오류도 여기서 드러난다. 내가 넣지 않은 기존 줄이 재서식되면 그대로 두고 보고에 적는다. `docs/resume-sync.md` 는 gitignore 되어 있어 prettier 가 건너뛰므로 넣지 않는다.

YAML 만 바뀌므로 lint · tsc · build 는 돌리지 않는다. 사용자가 화면으로 보겠다고 하면 `bun run dev` 를 백그라운드로 띄우고, 로그를 파일로 남기고, URL 과 PID 를 알린다.

- `git status --short` 와 `git diff --stat`. untracked 파일은 diff 에 안 나오므로 status 도 같이 보여 준다. 이번에 내가 만들지 않은 변경이 섞여 있으면 따로 알린다.
- 바뀐 activity
- 넣지 않은 후보
- 진행 중 항목: 실제 상태와, yaml 에는 완성된 구조로 썼다는 것. 머지되면 중점 지시를 붙여 다시 돌려 사실과 맞는지 확인하라고 안내한다
- 커밋하지 않았다는 사실: 커밋은 사용자가 직접 한다

## 흔한 실수

| 실수                                                              | 대신                                                                         |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 커밋·PR·버그 단위로 details 를 채움 (한 subject 에 9줄)           | 구조 결정 단위로, subject 2~4개 × details 1~3줄                              |
| details 를 함수·옵션 이름으로 채우거나, 반대로 일상어로만 풀어 씀 | 설계 개념은 전문 용어로, 도구는 이름으로 쓰고, 코드 식별자만 바꿔 쓴다       |
| yaml 에 "진행 중"이라고 씀                                        | 완성된 구조로 쓰고, 실제 상태는 보고와 메모 칸에 적는다                      |
| 인원 구성, 자사 제품이 쓴다는 사실처럼 당연한 것을 빈 곳으로 물음 | 배경과 전 / 후 수치만 묻는다                                                 |
| velog 매핑을 기술 스택 태그만 보고 제안함                         | `velog-posts.json` 에서 걸리는 글을 확인하고, 주제 글이 없으면 매핑하지 않음 |
| "업데이트해줘" 같은 일반 요청을 중점 지시로 봄                    | 특정 영역·작업을 가리킬 때만 중점 지시로 본다                                |
| 후보, 배치, 공개 범위를 묻지 않고 정함                            | 6단계 질문을 거친다                                                          |
| "wr 은 읽기 전용"이라며 fetch 를 생략함                           | fetch 는 한다. pull · 브랜치 생성 · 커밋은 하지 않는다                       |
| `gh` 를 레포 밖에서 돌리거나, PR 이 비어서 없다고 봄              | 레포 안에서 실제 이름을 얻고 `-R` 을 붙인다                                  |
| `docs/resume-sync.md`, `skill.yaml` 확인을 빠뜨림                 | 7단계 표를 끝까지 확인한다                                                   |
| lint · tsc · build 까지 돌림                                      | 8단계 두 가지만 한다. dev 서버는 사용자가 요청할 때만                        |
